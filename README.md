# SkinBase

Хранилище плащей для Minecraft с собственным API. Игроки загружают плащи на сайт,
надевают их, а **CustomSkinLoader** забирает капы в игру через плагин — без Mojang,
без сторонних хостингов картинок.

Система состоит из двух частей:

| Часть | Путь | Назначение |
|---|---|---|
| Сайт + API v3 | `~/skinbase` | Cloudflare Pages: фронтенд, REST API, D1 (метаданные), файлы на CatBox |
| Плагин CSL | `~/skinbase-csl-plugin` | Загрузчик профилей для CustomSkinLoader 15.x |

Продакшен: **https://skinbase-dov.pages.dev**

---

## 1. Сайт (`~/skinbase`)

### Стек

- **Cloudflare Pages Functions** — API и фронтенд (статика в `public/`)
- **D1** (SQLite) — пользователи, сессии, капы, экипировка, API-токены, бэкапы
- **CatBox** (`files.catbox.moe`) — PNG-файлы капов + альбом Capes
- Биндинги в `wrangler.jsonc`: `DB` (D1 `skinbase-db`), `SKINS_KV` (только для старых записей), `vars.CATBOX_ALBUM`

### Где физически лежат файлы

Все плащи лежат на **CatBox** в альбоме `CATBOX_ALBUM`. Отдельного пути
хранения для крупных капов нет, и он не нужен: CatBox не смотрит на размеры
картинки.

| Кап | Хранилище | Ссылка в `value` | Потолок |
|---|---|---|---|
| любой | **CatBox**, в альбоме `CATBOX_ALBUM` | `https://files.catbox.moe/<name>` | 200 МБ |
| legacy | Workers KV | `kv:<key>` | — |

> Раньше здесь стоял якобы существующий лимит CatBox в **4096 px**, и всё, что
> выше, писалось байтами в D1 (таблица `cape_blobs`, значение вида `d1:<id>`).
> Лимит был выдуман. Проверка на живых данных: из 44 плащей в базе шесть выше
> 4096 px по длинной стороне — максимум стек 1024×29696 весом 826 КБ — и все
> шесть лежат на CatBox и отдаются. Слой `0006_cape_blobs.sql` и вся ветка
> `d1:` удалены 2026-09-28. Прежде чем заводить снова «проблему» с размерами,
> проверяй её настоящей загрузкой через сайт.

Для работы CatBox-хранилища нужны env у Pages:

| Переменная | Где | Зачем |
|---|---|---|
| `CATBOX_ALBUM` | `vars` в `wrangler.jsonc` | короткий хеш альбома Capes |
| `CATBOX_USERHASH` | секрет Pages (`wrangler pages secret put CATBOX_USERHASH`) | userhash CatBox-аккаунта: добавление в альбом, удаление файлов |

### Структура

```
functions/
  _lib/auth.js      — авторизация (cookie-сессия / Bearer-токен), json(),
                     requireAuth(), requireDeleteAdmin() — снос плащей только админу
  _lib/cache.js     — кэш /api/v3/equipped и cape.json/cape.png в caches.default
  _lib/catbox.js    — CatBox: fileupload / addtoalbum / deletefiles, helpers по URL,
                     чтение kv:-источников при раздаче
  _lib/hash.js      — PBKDF2-пароли, генерация сессий и API-токенов, SHA-256
  _lib/cors.js      — CORS-обёртка (разрешает кросс-доменные запросы)
  _lib/image.js     — резолв ссылок на картинки (для бэкапов/старых записей)
  _lib/cape-check.js — проверка загружаемого плаща тем же кодом, что рисует превью
  _lib/limits.js    — потолок загрузки (20 МБ)
  _lib/storage.js   — уборка файла капа при откате и удалении
  _lib/obsolete.js  — заглушки снятых версий API (v1, v2 → 404)
  api/v3/…          — актуальный API (см. ниже)
  api/animated/v1/… — отдельная ветвь: анимированные капы (Stacked PNG)
public/             — SPA: index.html (обычные), animated.html (анимированные), app.js, animated.js, styles.css
  cape-format.js    — формат капа по байтам файла: IHDR, прозрачность, геометрия
                     стека, вердикт по крыльям. Без DOM, поэтому его импортирует
                     и серверная проверка загрузки — правила «что считать плащом»
                     не могут разойтись между сервером и браузером
  cape-texture.js   — превью: рисование, покадровая анимация, компоновка хвоста
                     и крыльев; переэкспортирует cape-format.js
migrations/         — схема D1 (wrangler d1 migrations apply)
wrangler.jsonc      — биндинги D1 + KV + vars.CATBOX_ALBUM
```

### База данных (D1)

| Таблица | Содержимое |
|---|---|
| `users` | id, username (unique), password_hash (PBKDF2), created_at |
| `sessions` | cookie-сессии: token, user_id, expires_at |
| `skins` | id, user_id, name, category (`cape`), value, tags, created_at |
| `equipped` | user_id (PK), cape_skin_id |
| `animated` | **анимированные капы** (Stacked PNG): id, user_id, name, value, tags |
| `animated_equipped` | **второй слот** экипировки: user_id (PK), animated_skin_id |
| `api_tokens` | name, token_hash (SHA-256, сам токен не хранится), revoked, last_used_at |
| `skin_backups` | JSON-бэкапы скинов, удалённых при миграции на v3 |

`value` капа — **ссылка на файл с префиксом хранилища**: `https://files.catbox.moe/<name>`
либо legacy `kv:<key>` (старый KV) или внешняя ссылка ImgBB. Клиентам наружу
отдаётся всегда `/api/v3/skin-file/<id>.png` — Worker раздаёт сам, независимо
от того, где файл.

### Права

Загрузка, просмотр, переименование и экипировка доступны любой авторизованной
учётке. **Удаление плаща — только админу**, и это единственное ограничение:

- `GGSHNIKK`, `Eonix`, `AuroraBreeze` — снос любого плаща (обычного и анимированного);
- все остальные — `403 Forbidden` на `DELETE .../skins/{id}`;
- без сессии — `401`.

Список лежит в `functions/_lib/auth.js` (`DELETE_ADMINS` + `requireDeleteAdmin`).
Сравнение имён регистронезависимое, а точное совпадение обязательно: `ggshnikk1`
и `ggshnik` админами не считаются. Список в коде, а не в D1: админов мало,
состав меняется правкой одной строки с деплоем, без новой миграции.

Проверка стоит **внутри** ветки `DELETE`, а не в общем `requireAuth`: иначе
чужой не смог бы даже открыть чужой плащ, и это была бы поломка галереи, а не
ограничение удаления. Флаг `canDelete` в ответах `/api/v3/me`, `/login`,
`/register` нужен только для того, чтобы прятать кнопку «✕» — серверная проверка
работает независимо от неё.

### API v3

Авторизация: cookie `__session` (браузер) **или** `Authorization: Bearer skb1_...` (API-токен).
Все ответы — JSON. Анонимные эндпоинты без авторизации: `equipped`, `skins/{user}/cape.*`, `me`, `login`, `register`.

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/v3/equipped` | Все игроки с надетым капом: `{count, users:[{username, equipped:{cape:{id,name,url}}}]}`. `?warm=1` — прогрев кэша |
| GET | `/api/v3/skins/{username}/cape.png` | PNG надетого капа игрока (прокси с хранилища, без редиректа) |
| GET | `/api/v3/skins/{username}/cape.json` | `{"cape": "https://…/api/v3/skin-file/<id>.png"}` — для CSL-плагина |
| GET | `/api/v3/skin-file/<id>.png` | Сам PNG капа: файл лежит на CatBox, но отдаётся с нашего домена (Worker проксирует + кэш CDN, CORS `*`) — клиенты получают «файл» без прямых catbox-ссылок |
| POST | `/api/v3/upload` | Загрузка капа: multipart `file` (PNG ≤ 20 МБ, проверка сигнатуры и заголовка IHDR), `name`, `tags`. Файл уходит на CatBox и в альбом; в ответе `skin.storage` = `catbox`. Если запись метаданных упала, файл с CatBox снимается — «сирот» не остаётся |

> **CatBox из Worker:** `files.catbox.moe` отдаёт 520 на запросы Cloudflare Workers без браузерного `User-Agent` — при проксировании обязательно ставить `User-Agent`/`Accept` браузера (см. `skin-file/[id].js`).
| GET | `/api/v3/skins?search=` | Общая библиотека: все капы всех пользователей, `search` фильтрует по имени/тегам |
| GET | `/api/v3/skins/{id}` | Кап по id (любой) |
| PUT | `/api/v3/skins/{id}` | Переименовать/сменить теги: `{name, tags}` (любой кап) |
| DELETE | `/api/v3/skins/{id}` | Удалить кап — **только админу** (см. «Права» ниже), иначе `403`. Файл с CatBox убирается через `deletefiles` — только если он больше никем не используется (CatBox дедуплицирует по содержимому). Порядок важен: файл сносится **до** обнуления `equipped.cape_skin_id`, иначе обрыв оставит игрока со ссылкой на несуществующий кап |
| GET/POST/DELETE | `/api/v3/equip` | GET — текущая экипировка; POST `{skin_id}` — надеть; DELETE — снять |
| GET/POST | `/api/v3/tokens` | Список API-токенов / создать `{name}` (токен показывается один раз) |
| DELETE | `/api/v3/tokens/{id}` | Отозвать токен |
| GET/POST | `/api/v3/login`, `/api/v3/register` | Аутентификация (`{username, password}`), сессия в cookie |
| GET | `/api/v3/me` | Текущий пользователь (или `{user: null}`). В `user.canDelete` — может ли он сносить плащи; SPA по нему прячет кнопку «✕» |
| GET/POST | `/api/v3/logout` | Завершить сессию |
| GET | `/api/v3/backup` | Статус бэкапа скинов из v1/v2: `{exists, count, download_url}` |
| GET | `/api/v3/backup/download` | Скачать бэкап JSON-ом (удаляется после выдачи) |
| POST | `/api/v3/backup/decline` | Отказаться от бэкапа |

Документация в человекочитаемом виде — на самом сайте: `/api/v3`.

### API animated/v1 (анимированные капы)

Анимированный кап — это **Stacked PNG**: все кадры лежат друг под другом в одном файле
(можно собрать из GIF/APNG утилитой **PixKit** `~/pixkit/conv.py stack …`). Отдельная ветвь
`/api/animated/v1`, чтобы не мешать анимацию с обычными капами: у игрока **два независимых
слота** — обычный (`/api/v3/equip`) и анимированный (`/api/animated/v1/equip`). Какой из двух
показывать — решает конфиг мода (каждый провайдер указывает свой эндпоинт).

Авторизация — как в v3 (cookie или Bearer). Анонимные: `equipped`, `skins/{user}/cape.*`.

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/animated/v1/equipped` | Все игроки с анимированным капом: `equipped: {animated: {id, name, url}}` |
| GET | `/api/animated/v1/skins/{username}/cape.png` | Stacked PNG игрока (прокси с хранилища) |
| GET | `/api/animated/v1/skins/{username}/cape.json` | `{"cape": …, "animated": true}` — маркер типа для модов |
| GET | `/api/animated/v1/skin-file/<id>.png` | Сам стек (PNG с нашего домена, прокси + кэш CDN) |
| POST | `/api/animated/v1/upload` | Загрузка: multipart `file`, `name`, `tags` — любой Stacked PNG |
| GET | `/api/animated/v1/skins?search=` | Каталог всех анимированных капов (общая библиотека) |
| GET/PUT/DELETE | `/api/animated/v1/skins/{id}` | Данные / редактирование (имя, теги) / удаление вместе с файлом из хранилища. Удаление — **только админу**, как в v3 |
| GET/POST/DELETE | `/api/animated/v1/equip` | Второй слот: GET — текущий; POST `{skin_id}` — надеть; DELETE — снять |

Никаких настроек вроде FPS или размера кадра мы нигде не храним и не передаём:
мод капов сам режет стек на кадры и сам задаёт темп показа.

### Кэширование и «умное хеширование»

Проблема, которую решаем: клиенты (CSL, Minecraft) кэшируют текстуры **по URL**.
Если отдавать кап всегда по одному URL (`cape.png`), смена капа не будет видна
до протухания кэша.

Решение: URL капа привязан к **конкретному файлу** — уникальному имени на CatBox
(`files.catbox.moe/<random>.png`), которое меняется при каждой загрузке/смене капа.
Клиент запрашивает по нику только короткий JSON (`cape.json`), получает прямую
ссылку файла и кэширует её. Сменил кап → сменилась ссылка → клиент скачивает
новый файл. Старый кэш «мёртв» и не мешает.

- `cape.json` / `cape.png` (обе ветки: v3 и animated/v1) кэшируются только в `caches.default`
  (private, 60 c) и принудительно инвалидируются при equip/unequip/delete
  (`invalidateEquippedCache` / `invalidateAnimatedCache`).
- `skin-file/<id>.png` — PNG с нашего домена через Worker-прокси (URL постоянный,
  файл живёт на catbox, ответ кэшируется на CDN).

### Тесты

```bash
npm test    # node --test tests/
```

`tests/cape-preview.browser.test.js` гоняет настоящий `public/app.js` в
Chromium через Playwright и проверяет жизненный цикл превью (см. грабли выше).
`tests/animated-preview.browser.test.js` — то же для `public/animated.js`:
крутит кадры, режет область, тумблер «Плащ/Крылья», вердикт по крыльям и
остановку за экраном. `tests/cape-texture.test.js` и
`tests/cape-texture.draw.browser.test.js` — разбор PNG/атласа и примитивы
отрисовки. `tests/delete-permissions.test.js` — права на снос плащей (403 для
чужих, 200 для админов, 401 без сессии) сквозным путём через оба handler'а.
Разметка для браузерных тестов берётся из настоящих `index.html` и
`animated.html`, а не собирается руками, чтобы DOM не устаревал.

Браузерные тесты гоняются в одном `node --test` параллельно, поэтому
проверки тайминга не ждут «сколько-нибудь миллисекунд»:
`window.__capeOffscreenGrace` (читывается в `app.js`/`animated.js` в момент
ухода карточки) позволяет задать паузу перед отпусканием WebGL-слота явно —
огромную для проверки удержания и нулевую для проверки освобождения. Без этого
тест мерил скорость машины: под нагрузкой два браузера с 14 контекстами
растягивают пару кадров за полторы секунды, и проверка падала на ровном коде.
Playwright **не** в `package.json` — тест ищет его в `node_modules` рядом и
сам скипается, если браузера или сети для CDN-скина нет, так что `npm test`
остаётся зелёным на машине без Chromium.

## 2. Плагин CustomSkinLoader (`~/skinbase-csl-plugin`)

Плагин добавляет источники **ElyBy** (скины) и **SkinBase** (капы) в loadlist CSL
и учит CSL работать с API v3 SkinBase.

### Как работает

- Jar кладётся в `CustomSkinLoader/Plugins/` и подхватывается через
  `ServiceLoader` (`META-INF/services/customskinloader.plugin.ICustomSkinLoaderPlugin`).
- Приоритеты (меньше = раньше в loadlist): **ElyBy — 9** (тип `ElyByAPI`,
  скины/капы), **SkinBase — 10** (тип `SkinBase`). CSL опрашивает ElyBy первым,
  потом SkinBase и **смешивает** результат: скин с ElyBy + кап со SkinBase.
- Загрузчик `SkinBaseProfileLoader` запрашивает
  `GET <root>/api/v3/skins/<username>/cape.json`, парсит
  `{"cape": "…/skin-file/<id>.png"}` и отдаёт CSL абсолютный URL капа
  (с id файла — см. «умное хеширование»).
- При любой ошибке (сеть, таймаут, 404, нет капа) возвращает `null` —
  CSL просто идёт к следующему источнику или к кэшу, ничего не сбрасывая
  и не ставя заглушку.
- Запросы к cape.json идут с `cacheTime = -1` (всегда свежий ответ),
  кэширует сам CSL (профиль ~30 мин).

### Сборка

```bash
./build.sh   # результат: build/SkinBase-CSL-Plugin.jar
```

Компилируется с `-source 8 -target 8` (байткод Java 8 — работает на любой JVM ≥ 8,
включая Java 21 в Minecraft 1.21). Зависимости только для компиляции (provided,
в рантайме есть в клиенте):

- `CustomSkinLoader-Common.jar` (вложен в Universal-версию: `META-INF/jar-jar/`)
- `authlib-6.0.54.jar`
- `gson-2.10.1.jar`

Пути к jar можно переопределить: `CSL_JAR`, `AUTHLIB_JAR`, `GSON_JAR`.

### Установка

1. Скопировать `build/SkinBase-CSL-Plugin.jar` в
   `CustomSkinLoader/Plugins/` (папка рядом с конфигом CSL).
2. Перезапустить игру. В логе CSL появится `Add a profile loader: SkinBase`.
3. В loadlist появятся `ElyBy` (приоритет 9) и `SkinBase` (10).
   Профиль игрока собирается из обоих: скин — ElyBy, кап — SkinBase.

## 3. Грабли (актуальные)

- **Chromium держит на странице 16 ЖИВЫХ WebGL-контекстов и молча отбирает
  самый старый** при превышении — карточка превью просто перестаёт рисовать
  (белое пятно), ни ошибки, ни исключения. Отсюда три правила в
  `public/app.js` (`MAX_CAPE_VIEWERS`, `forceContextLoss()`, освобождение вьюера
  при уходе карточки из зоны видимости). Замерено в браузере: 20 вьюеров подряд
  → 16 живых и 4 молчаливых трупа; `forceContextLoss()` срезает число жертв с
  44 до 12, но потолок 16 не поднимает. Симптом у пользователя выглядел как
  «превью ломается ПОСЛЕ прокрутки» — на самом деле ломалось всё, что успело
  догрузиться.
- **Крылья — это вырезка по альфе, поэтому вердикт по крыльям смотрит на
  прозрачность файла, а не на заполненность области.** У PNG без альфа-канала
  (colorType 2) область крыльев залита целиком всегда, и любая проверка
  «есть ли крылья» по покрытию даёт 100% и вешает «✓ крылья» на плащ без
  крыльев. На проде так ошибались 2 файла из 53. Прозрачность бывает не только
  альфа-каналом: у 17 файлов это палитра с `tRNS`, её видно только отдельным
  чанком. Всё это читает `pngTransparency()` в `public/cape-format.js`.
- **Плоское превью рисует композит «хвост + панель крыла», а не одну грань.**
  Одна грань 10×20 в квадратной карточке — узкая полоса с пустотами, которую
  пользователь читает как «текстура не загрузилась». Область бывает
  составной (`{parts:[…], gap}`), и при смене режима канвас пересоздаётся:
  хвост — 10×16, композит — 21×20, и втискивание одного в форму другого
  возвращает те же пустые поля.
- **Сырой файл плаща нельзя показывать `<img>`.** Для стека это каша всех
  кадров, для статичного капа — нечитаемый атлас 64×32. Если файл не
  прочитался, показывается надпись со ссылкой (`showUnreadable()`), а не
  содержимое файла.
- **`skinview3d.dispose()` не убирает `<canvas>` из контейнера** и не отпускает
  WebGL-контекст (`renderer.forceContextLoss()` надо звать самому). Без этого
  каждый цикл скролла подкладывает ещё один холст, а `.skin-preview` с
  `overflow:hidden` начинает резать картинку.
- **Не гасить `observeCapeCards()` из `renderEquipped()`.** После этого
  IntersectionObserver мёртв, и превью в библиотеке не появляются никогда.
- **Формат проверяется тем же кодом, который потом рисует превью.**
  `functions/_lib/cape-check.js` импортирует `public/cape-format.js` — поэтому
  сервер и браузер не могут разойтись в том, «что считать плащом». Обычный
  адрес принимает один кадр (в т.ч. HD 2048×1024) и отказывает стеку с
  понятным объяснением; анимированный принимает стек. Правила формата живут в
  браузерном модуле без DOM именно поэтому — иначе они бы разошлись.
- **Stacked PNG нельзя показывать целиком.** Это лист кадров друг под другом:
  `<img src>` отдаёт кашу из всех кадров, растянутую по высоте карточки.
  `public/animated.js` режет каждый кадр до области плаща (22×17) или крыльев
  (24×22) через `public/cape-texture.js` и крутит `createFramePlayer()`. Кадры —
  2D-канвас, поэтому потолка WebGL из 12 вьюеров тут нет; единственное
  ограничение — видимость: `hide()` гасит таймер, иначе страница с сотней
  карточек жжёт CPU на невидимых превью.
- **CatBox: файлы и альбомы.** Если не задан `CATBOX_USERHASH`, загрузки идут
  анонимно: файл не попадёт в альбом, а удалить его с catbox нельзя. Анонимные
  файлы могут удаляться catbox после долгого простоя — поэтому userhash обязателен.
- **Лимит альбома CatBox — 500 файлов.** Альбом Capes можно расширять до 500
  файлов, дальше либо чистить удалённые капы (есть DELETE), либо заводить
  след. альбом и менять `CATBOX_ALBUM`.
- **Потерянный KV-кап.** Кап id=68 («Broken», `kv:cap:4:…`) ссылается на файл,
  которого нет в KV. Лечение: перезалить кап через сайт.
- **Ники с §-кодами** (`§eНик`) URL-энкодятся CSL в `%C2%A7…` и в БД SkinBase
  не находятся → 404, CSL спокойно идёт дальше. Это норма.
- **Двойной ElyBy в loadlist.** Плагин добавляет ElyBy (9), а у самого CSL
  есть встроенный ElyBy (priority 400) — в loadlist их два. Не ломает,
  просто лишний запрос. При желании можно оставить только плагинный.
